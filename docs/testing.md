# 驗證方式與結果

## 自行驗證

```bash
node tests/make_test_media.mjs test-media/a.wav --minutes 4 --ppm 833
node tests/make_test_media.mjs test-media/b.mp4 --minutes 4 --ppm -694 --start 12:35:00.039 --plug 70
node cli/slate-sync.mjs test-media/a.wav test-media/b.mp4    # 命令列分析器（需 ffmpeg／ffprobe；--json、--lang en 等）
npm test                              # 全部：npm run check 加上 node --test（需 ffmpeg／ffprobe、Chrome 或 Edge）
```

測試都用 Node 內建的 `node --test`，可單獨執行：

| 測試 | 檢查的事 | 比對對象 |
|---|---|---|
| `node tests/check_web.js` | 網頁語法正確、四種語言的字串 key 一致 | — |
| `node tests/check_core.js` | 分析核心不用瀏覽器 API；node 直接分析 WAV 測試檔 | 真值（週期固定） |
| `tests/visual-code.test.mjs` | 場記板與分析核心的 tag 碼表、場記板畫的 ID 0–539（四種旋轉）、ID 公式 | 官方 `tag36h11.c`（`tests/data/tag36h11.json`）、固定期望值 |
| `tests/wave-pitch.test.mjs` | 場記板的 `cycleK()`／`waveHz()` 兩天逐秒（UTC、UTC+8）、分析核心的 `WAVE_HZ`／`cycleK()` | 獨立寫的規格公式與抽查值 |
| `tests/ltc-bits.test.mjs` | 場記板的 `countToTC()`／`ltcBits()`／`ltcChunk()` | 獨立的參考實作、DF 固定期望值、分析核心的解碼器 |
| `tests/read-audio.test.mjs` | 命令列從任何位置讀取音訊都不錯位（AAC 與 WAV） | ffmpeg 整段解碼 |
| `tests/cli-encoding.test.mjs` | 主控台不是 UTF-8（如 cp950）時報告仍完整印出 | — |
| `tests/clock-format.test.mjs` | 起點時鐘不出現 60 秒（五種週期） | 固定字串 |
| `tests/web/checks.test.mjs` | 網頁測試的每項檢查遇到錯的結果都會失敗 | 人工改壞的結果 |
| `tests/web/analyzer.test.mjs` | 建置後以 headless Chrome／Edge 跑網頁分析器 | 真值、命令列版、報告快照 |

場記板 `web/sync-slate.html` 的程式內嵌在頁面裡，測試以 `tests/lib/slate.mjs` 取出指定的函式，在 node 的 `vm` 執行。網頁測試的瀏覽器時區須與 `cam.mp4` 的真值相同（UTC+8）：Linux 以 `TZ=Asia/Taipei` 執行，Windows 的 Edge 不理會 `TZ`，用系統時區；不符時測試明確報錯。單獨執行網頁分析器：`node tests/web/run-analyzer.mjs 檔案… --av --out result.json --report report.txt`；報告措辭刻意修改時以 `node tests/web/analyzer.test.mjs --update` 更新快照。

測試產生器（`node tests/make_test_media.mjs --help` 列出全部選項）：`--minutes`、`--ppm`、`--ppm-end`（與 `--ppm` 之間線性變化，模擬機身變熱）、`--start`、`--plug`（只在頭尾各幾秒放波形碼）；`--ltc 24|25|29.97|30|23.976`（`--df`、`--ltc-channel`、`--ltc-with code|scene`、`--ltc-noise`、`--ltc-invert`，搭配 `--ppm`、`--start` 與 .m4a／.mp4 輸出的 AAC）；`--created start|end`、`--created-offset`、`--date`、`--tz`（MP4／MOV／M4A 寫 creation_time，WAV 寫 BWF time_reference）。產生器會印出 LTC 第一格的時間碼與位置、建立時間與 r 的真值。

生成器會印出設定的速度比例與真實長度，與分析結果比對即可。網頁由 `src/` 與 `web/` 建置到 `dist/`（需 Node；WebCodecs 需要安全環境，請用本機伺服器開啟）：

```bash
npm ci                          # 第一次：安裝 esbuild
npm run build                   # 建置到 dist/
npm run dev                     # 開發：改檔後自動重建，開啟 http://localhost:8000/sync-analyzer.html
```

產生器只需要 Node 與 ffmpeg（PATH 中；輸出 WAV 且不寫建立時間時不需要 ffmpeg）：音訊在 JS 以陣列合成，畫面算成灰階 raw 影格經 stdin 交給 ffmpeg 編碼。波形碼的脈衝與載波、tag 的繪製與 LTC 的取樣都以 vm 執行場記板本身的函式，與場記板一致；場記板本身算錯時由上表的獨立比對抓到。畫面碼（AprilTag，規格見 [visual-code.md](visual-code.md)）：

```bash
node tests/make_test_media.mjs test-media/v.mp4 --visual --minutes 3 --plug 60 --fps 29.97 --av-offset 25
node tests/make_test_media.mjs test-media/w.mp4 --visual --minutes 3 --plug 60 --fps 25 --audio none --start 12:38:00.5
node cli/slate-sync.mjs test-media/v.mp4 test-media/w.mp4 --av
```

`--visual` 模擬攝影機拍手機螢幕：曝光區間以每格的時間為中心、長 `--shutter` 格，跨過整秒時新舊 tag 依時間比例混合；`--ppm` 同時作用於畫面與聲音軌，`--av-offset` 為畫面相對聲音的偏移。產生器印出實際用的編碼器與 GOP（預設 1 秒，`--encoder auto` 先試 NVENC）。其他畫面選項：`--fps`、`--size`、`--codec h264|h265`、`--encoder auto|nvenc|cpu`、`--gop`、`--tag-size`、`--blur`（高斯模糊，像素）、`--exposure`（亮度與自動曝光起伏）、`--tilt`（手機繞垂直軸傾斜，度）、`--audio code|scene|none`。`--created end` 搭配 `--visual` 時，建立時間與 r 以影片長 nfr / fps 計算（分析器以畫面軌的長度為準）。

此測試同時發現並修正一個錯誤：開頭讀到分鐘標記、結尾沒有時，兩端合併換算會把開頭約 60 秒的範圍折疊，產生錯誤但看似正常的結果。現已修正，並加上防護：速率偏差超過 1% 或擬合殘差超過 5 ms 時判定為讀取錯誤，不輸出結果。

### 用上每秒所有脈衝的前緣

每秒除了同步脈衝，數字脈衝的起點也是固定的；場記板每秒用一個從零相位開始的振盪器，所以每個脈衝開啟時的波形位置可由音高與時間位置算出。分析器把每秒所有脈衝換算回該秒起點後平均，並自動比較：每秒時間的離散度較小的算法才採用。

| 只錄一端 11 秒，各 12 次 | 只用同步脈衝 | 用上所有脈衝 |
|---|---|---|
| 乾淨 | 0.23 ppm | 自動改用同步脈衝（結果相同） |
| 雜訊 SNR 20 dB | 64.8 ppm（最大 188） | 24.3 ppm（最大 77） |
| 迴響（約 0.5 m） | 16.2 ppm | 16.5 ppm（迴響影響同一秒的所有脈衝，平均無幫助） |

測試產生器同時修正為和場記板一致：每秒一個振盪器開關出各脈衝，且整秒依錄音設備的時鐘比例縮放（包括音高與脈衝間隔）。所有模式的回歸測試與網頁版、Python 版比對皆一致。

### 波形碼音高的 9 分鐘循環（Python 版）

`tests/wave-pitch.test.mjs`：以 vm 執行場記板的 `cycleK()`／`waveHz()`，連續兩天逐秒（UTC 與 UTC+8，含跨午夜，另抽查整秒內的毫秒）與獨立寫的規格公式（與產生器相同）比對，172800 秒全部一致；場記板與分析核心的 11 個音高與固定的音高表相同；相鄰兩秒都不同音；分析核心的 `cycleK()` 由秒數與音高解回全部 540 個 k（都在 0–539、各一次），其餘 120 種組合判為讀錯。

回歸：5 個 WAV（4 分鐘 +833 ppm；−694 ppm 頭尾各 70 秒；10 分鐘 +200 ppm 頭尾各 30 秒；20 分鐘 +800 → +900 ppm `--full`；跨午夜 −300 ppm），各以預設、`--minute`、`--only head` 與三檔對齊執行，與修改前的分析器比較：

| 情況 | 結果 |
|---|---|
| 新公式檔 | 循環由 60 → 540、3600 → 10800 秒；速度比例差 ≤ 8×10⁻¹¹，起點差 ≤ 0.12 µs，預估誤差差 ≤ 3×10⁻⁵ ms；音高排除 0 秒 |
| 新公式檔，只讀一端 7 秒（`--only head`） | 速度比例差 0.80 ppm（量測精度 ±1.89 ppm）：音高不同，每秒前緣的取樣內插誤差不同 |
| 兩檔起點相差 4 分 15.25 秒（+300 ppm 對 −200 ppm） | 新公式：循環 540 秒，標示 190.250／445.500（真值 190.25／445.5），對齊 +255.326577 秒（理論 255.326575） |

讀不到足夠的音高時退回只用秒數（採用門檻：至少 3 秒推出同一個 k 且過半）。`tests/generator.test.mjs` 以新公式的短檔回歸：只有 2 秒波形碼時週期為 60 秒，3 秒時為 540 秒，起點都在預估誤差內。

### 測試產生器的 LTC

`tests/ltc-bits.test.mjs`：以 vm 執行場記板的 `countToTC()`／`ltcBits()`，與獨立的參考實作（與產生器相同的算法）逐格比對 24、25、29.97 DF、29.97 NDF、30、23.976 各約 5400 格（午夜前後、每分鐘與每 10 分鐘邊界、全天隨機 3000 格），時間碼與 80 個位元全部相同；再以模擬的 AudioContext 執行場記板的 `ltcChunk()`（4 個區塊、32 格、跨午夜），輸出的 51200–64064 個取樣與參考實作逐點相同（位元、極性、振幅 0.5、格起點、跨區塊連續），分析核心的 `ltcDecode()` 從這些取樣解回連續的格數，`tcToCount()` 把每個時間碼換回同一個格數。DF 抽查（固定期望值）：每分鐘跳過 ;00、;01，每 10 分鐘不跳，一天 2589408 格。

錄音端以錄音設備的時鐘、每個取樣取前後半個取樣間隔的平均值合成。以零交越檢查：25 fps +833 ppm 的第一個交越在 30.2752 ms（理論 30.2752），半位元間隔擬合為 +833.000 ppm；29.97 NDF −694 ppm 為 −694.000 ppm；AAC、反相、訊雜比 20 dB 時 −500 ppm 擬合為 −499.943 ppm。

### AAC 開頭讀取（回歸測試）

### 畫面碼（AprilTag）

### 網頁分析器自動測試

`tests/web/run-analyzer.mjs` 先建置，再在本機伺服器以外框頁（`tests/web/harness.html`）載入 `dist/sync-analyzer.html`，把 `tests/fixtures/` 的測試檔交給分析器並收回結果；分析器本身不為測試修改。`tests/web/analyzer.test.mjs` 檢查（檢查邏輯在 `tests/web/checks.mjs`，`checks.test.mjs` 以改壞的結果確認每項都會失敗）：

- 與真值的誤差在報告自己的預估誤差內（另加半個取樣 0.0104 ms，產生器把每秒取整到取樣點）；
- 與命令列版的差異在容許值內（速度比例 0.05 ppm、起點 0.001 ms、長度 0.01 ms，約為兩版實測最大差異的 2 倍；聲畫偏移 0.05 ms，因兩版縮小影格的方式不同）；
- 週期（wave 10800、aac／cam／picture 540、ltc 86400）與音高排除數 0 是真值裡固定的期望值，起點以真值的週期換算；預估誤差（`uncPpm`、`worstMs`）不超過真值的上限（產生時實測值的 2 倍）；cam.mp4 建立時間推定的 r 與真值（以影片長 nfr / fps 算，−0.265 秒）相差 ≤ 0.02 秒；
- 瀏覽器的時區與真值記錄的時區（cam.mp4 的建立時間以 UTC+8 寫入）相同；
- 繁中文字報告與快照（`tests/web/snapshots/`）相同，數字以 `#` 取代、「硬體解碼失敗」那一行拿掉後比對。

### 命令列改為 Node（ADR-0001）

網頁與命令列改用同一份分析核心（`src/core/`），命令列 `cli/slate-sync.mjs` 只以 ffprobe／ffmpeg 讀檔。

- `tests/fixtures/` 全部 5 個檔案：命令列與網頁版的速度比例、起點、校正後長度差異皆小於 10⁻⁹（顯示位數內為 0），聲畫偏移差 < 0.0001 ms，LTC 檔也一致；只有預估誤差差 0.00001 ms（cam.mp4，AAC 解碼器不同）。網頁版的結果與四種語言的文字報告與搬移前逐字相同。

## 尚未驗證

- 實際設備的錄音路徑（手機耳機輸出 → 線材 → 錄音機或攝影機輸入）
- 剪輯軟體內部的速度或長度輸入精度
- Safari、Firefox 上的網頁版分析器（僅以 Chromium 測試）
- 實際在 iPhone、Android 上安裝 PWA（Wake Lock 在主畫面 App 中的行為依系統版本而異）
- 日文、韓文介面在實機上的字形與字距（無頭模式使用本機替代字型）
- 畫面碼以實機拍攝手機螢幕：反光、摩爾紋、滾動快門、自動曝光、螢幕更新延遲（測試影片為合成畫面，曝光區間以每格時間為中心）
- 場記板實際的畫面碼切換時序與方波、波形碼是否同一刻（測試影片以理想切換產生）
- 可變影格率（手機錄影）、長 GOP 或全 I 格編碼、直拿（旋轉中繼資料）的畫面碼讀取與成本
- 畫面碼的 `--full` 抽查中段、`--only`（程式已接上，未以測試影片驗證）
- cuda 以外的硬體解碼（d3d11va，以及沒有 NVIDIA 顯示卡的機器）
- Node 命令列在真的 cp950 主控台視窗中的輸出（`cli-encoding.test.mjs` 只測導向管線的輸出）
- 網頁版分析器的畫面碼解讀
- 波形碼音高循環：網頁版分析器、以新版場記板實際錄音（只以合成檔驗證）
- 分析器讀 LTC 與檔案建立時間（[ltc.md](ltc.md)、[start-time.md](start-time.md)）：測試產生器已能產生，分析器尚未實作
- 產生器 LTC 第一格的格數換算（23.976、29.97 NDF）與場記板 `ltcStart()` 相同公式，但未以 node 直接執行 `ltcStart()` 比對；漂移鎖定（每次 ±1 取樣）未模擬
