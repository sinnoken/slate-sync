# 驗證方式與結果

## 自行驗證

```bash
python tests/make_test_media.py test-media/a.wav --minutes 4 --ppm 833
python tests/make_test_media.py test-media/b.mp4 --minutes 4 --ppm -694 --start 12:35:00.039 --plug 70
python python/slate_sync.py test-media/a.wav test-media/b.mp4
python tests/check_read_audio.py       # 從任何位置讀取音訊都不錯位（AAC 與 WAV）
python tests/check_cli_encoding.py     # 主控台不是 UTF-8（如 cp950）時報告仍完整印出
python tests/check_visual_code.py      # 各處內嵌的 tag 碼表一致、每個 ID 都偵測得到
python tests/check_wave_pitch.py       # 波形碼音高：場記板、產生器、分析器的公式一致（需要 node）
python tests/check_ltc_bits.py         # 產生器的 LTC 與場記板逐格、逐取樣相同（需要 node）
node tests/check_web.js               # 網頁語法正確、四種語言的字串 key 一致
python tests/web/check_analyzer.py    # 以 headless Chrome／Edge 跑網頁分析器，與真值、命令列版、報告快照比對
```

測試產生器的其他選項：`--old-pitch`（舊版場記板的載波，不帶 9 分鐘循環）；`--ltc 24|25|29.97|30|23.976`（`--df`、`--ltc-channel`、`--ltc-with code|scene`、`--ltc-noise`、`--ltc-invert`，搭配 `--ppm`、`--start` 與 .m4a／.mp4 輸出的 AAC）；`--created start|end`、`--created-offset`、`--date`、`--tz`（MP4／MOV／M4A 寫 creation_time，WAV 寫 BWF time_reference）。產生器會印出 LTC 第一格的時間碼與位置、建立時間與 r 的真值。

生成器會印出設定的速度比例與真實長度，與分析結果比對即可。網頁版分析器請用本機伺服器開啟（WebCodecs 需要安全環境）：

```bash
python -m http.server 8000      # 在 repo 根目錄執行，然後開啟 http://localhost:8000/web/sync-analyzer.html
```

畫面碼（AprilTag，規格見 [visual-code.md](visual-code.md)）另需 `pip install pupil-apriltags`（測試影片另需 pillow）：

```bash
python tests/check_visual_code.py          # 三處碼表一致、ID 0–539 繪製後讀回、ID 公式
python tests/make_test_media.py test-media/v.mp4 --visual --minutes 3 --plug 60 --fps 29.97 --av-offset 25
python tests/make_test_media.py test-media/w.mp4 --visual --minutes 3 --plug 60 --fps 25 --audio none --start 12:38:00.5
python python/slate_sync.py test-media/v.mp4 test-media/w.mp4 --av
```

`--visual` 模擬攝影機拍手機螢幕：曝光區間以每格的時間為中心、長 `--shutter` 格，跨過整秒時新舊 tag 依時間比例混合；`--ppm` 同時作用於畫面與聲音軌，`--av-offset` 為畫面相對聲音的偏移。產生器印出實際用的編碼器與 GOP（預設 1 秒，`--encoder auto` 先試 NVENC）。

### 用上每秒所有脈衝的前緣

每秒除了同步脈衝，數字脈衝的起點也是固定的；場記板每秒用一個從零相位開始的振盪器，所以每個脈衝開啟時的波形位置可由音高與時間位置算出。分析器把每秒所有脈衝換算回該秒起點後平均，並自動比較：每秒時間的離散度較小的算法才採用。

| 只錄一端 11 秒，各 12 次 | 只用同步脈衝 | 用上所有脈衝 |
|---|---|---|
| 乾淨 | 0.23 ppm | 自動改用同步脈衝（結果相同） |
| 雜訊 SNR 20 dB | 64.8 ppm（最大 188） | 24.3 ppm（最大 77） |
| 迴響（約 0.5 m） | 16.2 ppm | 16.5 ppm（迴響影響同一秒的所有脈衝，平均無幫助） |

測試產生器同時修正為和場記板一致：每秒一個振盪器開關出各脈衝，且整秒依錄音設備的時鐘比例縮放（包括音高與脈衝間隔）。所有模式的回歸測試與網頁版、Python 版比對皆一致。

### 波形碼音高的 9 分鐘循環（Python 版）

`tests/check_wave_pitch.py`：以 node 執行場記板的 `cycleK()`／`waveHz()`，連續兩天逐秒（UTC 與 UTC+8，含跨午夜，另抽查整秒內的毫秒）與產生器的 `wave_hz()`、分析器的 `pitch_index()` 比對，172800 秒全部一致；三處的 11 個音高相同；相鄰兩秒都不同音；分析器由秒數與音高解回全部 540 個 k，其餘 120 種組合判為讀錯。

回歸：5 個 WAV（4 分鐘 +833 ppm；−694 ppm 頭尾各 70 秒；10 分鐘 +200 ppm 頭尾各 30 秒；20 分鐘 +800 → +900 ppm `--full`；跨午夜 −300 ppm），各以預設、`--minute`、`--only head` 與三檔對齊執行，與修改前的分析器讀舊公式檔比較：

| 情況 | 結果 |
|---|---|
| 新公式檔 | 循環由 60 → 540、3600 → 10800 秒；速度比例差 ≤ 8×10⁻¹¹，起點差 ≤ 0.12 µs，預估誤差差 ≤ 3×10⁻⁵ ms；音高排除 0 秒 |
| 新公式檔，只讀一端 7 秒（`--only head`） | 速度比例差 0.80 ppm（量測精度 ±1.89 ppm）：音高不同，每秒前緣的取樣內插誤差不同 |
| 舊公式檔（`--old-pitch`，與修改前的產生器逐位元組相同） | 全部退回只用秒數（60／3600 秒）；速度比例差約 10⁻⁹，起點差約 1 µs，只讀一端 7 秒時 0.77 ppm。舊音高被比對到最近的五聲音階音，前緣校正因此差幾 µs |

### 畫面碼（AprilTag）

測試影片以 `--visual` 產生：720p、3 分鐘、頭尾各 60 秒有場記板，H.264（libx264，GOP 1 秒），聲音軌為波形碼；另有只有畫面與 H.265 各一組。分析器以硬體解碼（cuda）。

- `tests/check_visual_code.py`：場記板與測試產生器的碼表、位元位置與 pupil-apriltags 內建的官方 tag36h11 及官方 `tag36h11.c` 相同；ID 0–539 以每格 4 像素、1 格靜區繪製後全部讀對；ID 公式抽查 10 個時間（含 10:59:59→11:00:00、23:59:59→00:00:00），連續兩天逐秒連續。
- 19 組（23.976、24、25、29.97、50、59.94 fps 各有、無聲畫偏移；另加模糊 2.5 px、曝光起伏 ±50%、透視 35°、快門 360°（每格都混合）、只有畫面、H.265、tag 佔短邊 15%；時鐘 −833～+833 ppm，起點含跨整點與跨午夜）：

| 項目 | 結果 |
|---|---|
| 秒號與 ID | 333 個邊緣，ID 錯 0、真值在區間外 0 |
| 純畫面：速度比例誤差 | 1.4–165 ppm，19 組都在報告的估計誤差內（估計 ±97–±244 ppm） |
| 純畫面：起點誤差 | 1.1–19.2 ms，19 組都在預估誤差內（±8.8–±22.0 ms） |
| 聲畫偏移 | 18 組有聲音軌 × 頭尾 36 個值都在報告的 ±半格區間內；誤差最大 19 ms（23.976 fps，半格 20.9 ms） |
| 聲畫漂移 | 真值 0，18 組都在估計誤差內，無誤報 |
| 跨檔案起點相差 3 分 2.334 秒（只有畫面，29.97 fps +300 ppm 對 25 fps −200 ppm） | 對齊 +182.404622 秒（理論 182.389），比對窗 ±4.5 分鐘 |

畫面碼的預估誤差有一個下限（h = 半格，`vis_floor()`）。每端的殘差 F 取下列最大者：影格率整除 1 秒（依規格）、可變影格率或尚無擬合時為 h；每秒相位移動 frac(fps × 速度比例) 格，扣掉速度誤差可解釋的部分後掃過 k 格時為 h / max(1, k)；擬合後各邊緣實際落在影格中的相位，n 個相位的最大環狀間隙 g 留下 h × min(1, g + 1/n)。速度誤差下限：頭尾兩端為 2F / 兩端平均邊緣時間的距離，只有一端時為 3F / 該端跨度；檔案任何位置的下限為 F + 速度誤差下限 × 檔案頭尾到較近一端平均邊緣時間的最遠距離。讀到誤差不再下降 5 秒即停（矩陣中每端約讀 9 秒）。

以模擬影格（每組 10 種起始相位）驗證這個下限：29.5 fps（每秒相位移動半格，只落在 2 個相位）讀 120 秒實際誤差 8.5 ms，原本只估 ±1.2 ms，現在 ±8.6 ms；只有一端（檔案 120 秒，場記板在 30–80 秒）時，23.976 fps +833 ppm 實際 71 ms、原本估 ±20.9 ms，現在 ±104 ms；29.97、59.94、23.976、29.83、30、25 fps 讀 10–120 秒的各種組合都沒有超出估計。

硬體與軟體解碼（4 個 720p 檔）：每格的 ID、邊緣與擬合結果完全相同。

### 網頁分析器自動測試

`tests/web/run_analyzer.py` 在本機伺服器以外框頁（`tests/web/harness.html`）載入 `web/sync-analyzer.html`，把 `tests/fixtures/` 的測試檔交給分析器並收回結果；分析器本身不為測試修改。`tests/web/check_analyzer.py` 檢查：

- 與真值的誤差在報告自己的預估誤差內（另加半個取樣 0.0104 ms，產生器把每秒取整到取樣點）；
- 與命令列版的差異在容許值內（速度比例 0.05 ppm、起點 0.001 ms、長度 0.01 ms，約為兩版實測最大差異的 2 倍；聲畫偏移 0.05 ms，因兩版偵測器不同）；
- 繁中文字報告與快照（`tests/web/snapshots/`）相同，數字以 `#` 取代後比對。

測試檔由 `tests/fixtures/make_fixtures.py` 以固定參數產生（640×360、libx264，不含 HEVC，合計約 3 MB）；頭尾模式要求兩端相隔 60 秒以上，所以長檔為 80 秒。本機 Edge 全部約 40 秒。

- 實際設備的錄音路徑（手機耳機輸出 → 線材 → 錄音機或攝影機輸入）
- 剪輯軟體內部的速度或長度輸入精度
- Safari、Firefox 上的網頁版分析器（僅以 Chromium 測試）
- 實際在 iPhone、Android 上安裝 PWA（Wake Lock 在主畫面 App 中的行為依系統版本而異）
- 日文、韓文介面在實機上的字形與字距（無頭模式使用本機替代字型）
- 畫面碼以實機拍攝手機螢幕：反光、摩爾紋、滾動快門、自動曝光、螢幕更新延遲（測試影片為合成畫面，曝光區間以每格時間為中心）

- 可變影格率（手機錄影）、長 GOP 或全 I 格編碼、直拿（旋轉中繼資料）的畫面碼讀取與成本
- 畫面碼的 `--full` 抽查中段、`--only`（程式已接上，未以測試影片驗證）
- cuda 以外的硬體解碼（d3d11va，以及沒有 NVIDIA 顯示卡的機器）
- 網頁版分析器的畫面碼解讀
- 波形碼音高循環：網頁版分析器、以新版場記板實際錄音（只以合成檔驗證）
- 分析器讀 LTC 與檔案建立時間（[ltc.md](ltc.md)、[start-time.md](start-time.md)）：測試產生器已能產生，分析器尚未實作
